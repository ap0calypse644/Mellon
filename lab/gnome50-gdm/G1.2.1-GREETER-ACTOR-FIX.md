# Mellon G1.2.1 — Correct GNOME 50 greeter actor layering

## Root cause (from GNOME Shell 50 source, not inferred from screenshot)

The first G1 greeter source targeted
`Main.screenShield?._dialog?._backgroundGroup`. This is from the
user-unlock-screen architecture, not from GNOME's distinct GDM LoginDialog.
The live VM confirmed installation, enabled-extensions, and photo asset
read access. The absence of a missing-actor warning was misleading because
G1 returned silently after 90 unsuccessful polls.

Verified against the **GNOME Shell gnome-50** source:

- `js/ui/main.js`: GNOME creates ScreenShield and calls
  `screenShield.showDialog()` after the greeter startup preparation.
- `js/ui/screenShield.js`: `_lockDialogGroup` is the common
  container; `_ensureUnlockDialog()` creates the current LoginDialog
  as `new constructor(this._lockDialogGroup)`.
- `js/gdm/loginDialog.js`: `LoginDialog._init(parentActor)` directly
  invokes `parentActor.add_child(this)`. It **does not define**
  `_backgroundGroup`. Its custom `vfunc_allocate()` only allocates
  five built-in child widgets, so attaching an image as a new child
  of LoginDialog is NOT a reliable rendering solution.
- `data/theme/gnome-shell-sass/widgets/_login-lock.scss`: the
  `.login-dialog` class does not explicitly paint an opaque full-screen
  background in the current gnome-50 theme source.

## G1.2.1 patch

The non-reactive, non-focusable, image-only actor is now created as a
**sibling below** the native LoginDialog in
`Main.screenShield._lockDialogGroup`, and size-bound to the
`_lockDialogGroup` actor. The LoginDialog itself, its allocation,
user list, password entry, keyboard focus, user verification and
session selection are untouched. The source logs a safe
`[Mellon Greeter G1.2.1]` message on activation and on successful mount
(no credentials, keystrokes or prompt state ever logged). If the
expected GNOME actor relationship is missing, no actor is added and
after a bounded polling window a warning is emitted.

## VM-only patch sequence

**Backup:** `MELLON-GDM-PREINSTALL-001` qcow2 + UEFI vars + libvirt
XML are hash-verified and remain unchanged.

Run tests and stage only the new `extension.js` into test1's VM home:

```bash
(
    set -euo pipefail
    cd "$HOME/go/src/ap0calypse644/Mellon"
    git -c core.hooksPath=/dev/null pull --ff-only origin main
    node lab/gnome50-gdm/test-g1.mjs
    node lab/gnome50-gdm/test-g1-runtime.mjs
    node lab/gnome50-gdm/test-g121-update.mjs
    bash lab/gnome50-gdm/stage-g121-update-to-vm.sh
)
```

The staging helper does **not** change GDM.

Only if staging passes, update the **test VM** GDM source with
interactive guest sudo (this does NOT modify dconf or trigger a restart):

```bash
(
    set -euo pipefail
    ssh -tt mellon \
      'sudo bash /home/test1/.local/state/mellon-gdm/g1-update-003/update-g121-in-guest.sh'
)
```

The update script verifies the unchanged vendor/admin dconf files and
the exact **previous G1 source signature**, preserves the original
G1 `extension.js` under a root-only backup, installs a dedicated
rollback command first, then atomically replaces just
`/usr/share/gnome-shell/extensions/mellon-greeter@local/extension.js`.

After success, reboot **only** the VM:

```bash
(
    set -euo pipefail
    virsh -c qemu:///system reboot mellon-gnome50-lab
)
```

Observe the photo at both GDM user-list and password prompts, and
confirm the original native password form is accessible. Do not enter
passwords into chat logs or paste full process environments.

**Read-only post-test diagnostic** (while VM is at the GDM greeter):

```bash
(
    set -euo pipefail
    cd "$HOME/go/src/ap0calypse644/Mellon"
    bash lab/gnome50-gdm/diagnose-g1-greeter.sh
)
```

**Rollback only the G1.2.1 source** if photo placement is wrong:

```bash
(
    set -euo pipefail
    ssh -tt mellon \
      'sudo /usr/local/sbin/mellon-greeter-g121-rollback'
    virsh -c qemu:///system reboot mellon-gnome50-lab
)
```

If the greeter remains unusable, the separate full G1 uninstall is
available at `/usr/local/sbin/mellon-greeter-g1-rollback` (VM only).
BlackPearl's actual GDM and its lockscreen extension are NEVER modified
by these scripts.

## G1.2.1 guest Node.js correction

GNOME 50's guest does not have Node.js. The failed root updater stopped before copying the backup or changing the installed extension. Syntax validation remains on BlackPearl and CI; the guest verifies source SHA256 and expected signatures. Both update and rollback scripts now run without Node.js. The fixed staging uses a fresh `g1-update-003` directory, preserving the prior `g1-update-002` contents.
