# G1.8 / M8.4 — Unified Eight-Stage Mapping (VM-only)

**Status:** implemented in repository and tested synthetically. Actual GNOME
50.1 VM behavior is not yet validated; no BlackPearl host changes authorized.

## Design

The old Observatory mapping HUD was effectively static until the final
completion: stages 1–7 all displayed the same "MAPPING CONSTELLATION"
message, and only the full eight-segment state animated. G1.8 makes the
mapping progression explicit and legible on both the lock screen and GDM.

- Empty: **AWAITING INPUT**
- First through seventh stage: **MAPPING 01 / 08**, **MAPPING 02 / 08**,
  ... **MAPPING 07 / 08**
- Eighth, after all photographic source stars light: **CONSTELLATION MAPPED**
- Each newly reached partial stage momentarily scales to 1.82× wide /
  1.56× tall with a 560 ms sinusoidal flare. If multiple stages arrive
  in one source-star update, only the newly reached segments pulse.
- Backspace immediately extinguishes surplus progress, resets all
  segment scales, and cancels any pending partial pulse.
- Eight-stage **final completion remains exactly the original M7.1
  dramatic nebula-star completion wave**; its HUD glint and persistent
  static bright mapped segments remain unchanged. There is no extra
  full-screen effect and no artificial stars.
- Stages depend only on the activated original-source-photography star
  mask via the existing M6.4 mapping function; the HUD never sees
  password strings, raw keystrokes, verifier state, or other credentials.
- The stage pulse is advanced by the **already-running 62 ms photographic
  star animation**. It adds **zero new GLib timers** and zero idle
  animation loops. The 5-second lattice scan still has its original
  50 ms temporary frame timer and bounded 1.85 s animation.

The visual-only `hud-progress.js` is **byte-for-byte identical** in the
two GNOME extensions and is protected by cross-implementation parity
checks. Existing `stellar-effects.js` and all twelve source-star
photographs remain untouched.

## Scan consistency

Previously, M8.3.2 called `cancelIntro()` whenever GNOME rejected a
password, permanently stopping its future 5-second grid scans. GDM
already preserved those scans. M8.4 now keeps scanning after an
incorrect-password warning, just like GDM, and its intro adopts the
GDM-tested resize/reflow logic that restarts scans rather than disabling
them. SHOW LOGIN still hides the entire lock-screen decoration, so the
original GNOME recovery interface remains usable.

The lock-screen signal-disconnect hardening from the immediately
preceding parity audit is included in M8.4.

## Source changes

**Both:** `hud-progress.js` and `observatory-hud.js` (shared mapping
readout and pulse).

**M8.4 lock:** `extension.js` (survive failed attempts, disconnect old
buffers), `observatory-intro.js` (safe continuous scan after resize),
`metadata.json`.

**G1.8 GDM:** `extension.js` (version marker only), `metadata.json`.
No change to GDM authentication, native account handoff, session choice,
or any photographic source-star assets.

## Real VM test checklist

1. GDM login: 12-scene photo, account auto-selection, SHOW LOGIN, and
   original constellation ignition unchanged.
2. Enter passwords slowly through 1–8 visual stages: text increments
   from `MAPPING 01 / 08`; corresponding new segment(s) briefly pulse.
   This is *visual stage count*, not an authentication success signal.
3. On Backspace the number decreases, extra segments disappear instantly,
   and no obsolete pulse sticks around.
4. At stage eight the original strong completion wave and persistent
   luminous stars/edges remain, with eight bright HUD segments.
5. Enter an incorrect password: **UNAUTHORIZED ACCESS** shows, progress
   resets, and the 5-second grid continues on both GDM and lock screen.
6. Login, lock the VM session, unlock via M8.4; repeat 3 cycles.
7. If practical change the VM resolution, verify both lock and GDM grids
   continue their five-second cadence. The exact astronomical photo and
   HUD alignment must remain intact.
8. SHOW LOGIN must still reveal GNOME's fully usable native password form.

No passwords or secret authentication logs should be shared.
