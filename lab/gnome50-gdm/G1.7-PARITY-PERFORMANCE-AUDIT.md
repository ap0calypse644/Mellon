# Mellon G1.7 → M8.3.2 parity and performance audit

**Audit scope:** source-level review of the GDM test greeter G1.7 and
the separately installed M8.3.2 lock screen. No VM/host instrumentation
was performed for this report. Source tests cannot establish measured
CPU/RAM usage or real GNOME 50 compositor behavior.

## Verified source parity

The following **six modules must stay byte-for-byte identical** between
`lab/gnome50-m8/` and
`lab/gnome50-gdm/greeter-extension/`, enforced by
`test-g17-parity-performance.mjs` in both the M8 and GDM CI workflows:

| Shared engine | Result |
| --- | --- |
| `scene-data.js` — curated scene/activation/edge/cover geometry | Identical |
| `stellar-effects.js` — ignition, completion, persistent glow | Identical |
| `failure-tracker.js` — read-only failed-authentication count | Identical |
| `hud-state.js` — Observatory metadata | Identical |
| `hud-progress.js` — stage segments and wave progression | Identical |
| `hud-intro-state.js` — 5s scan timing and cell strengths | Identical |

The lock/GDM `hud-layout.js`, `observatory-hud.js`,
`observatory-intro.js`, and `stylesheet.css` are intentionally
**not identical**: GDM has a native account list and changes its
recovery-button rectangle by mode; its scan must also survive
GDM allocation/resizing. GDM's stylesheet must retain all original
M8 styles as a prefix, plus the G1.6B account-picker styles.
These intentional differences are also guarded by tests.

**Important:** a 5s scan intentionally redraws during part of each
cycle, so CPU must be measured with the recurring scan active before
claiming a production budget. Source-level analysis indicates no
permanently active 62ms star animation when the input is idle,
but does not prove real compositor idle utilization.

## Concrete bug fixed in lock-screen source

M8.3.2 previously connected `notify::length` to each password
buffer but retained no signal ID for disconnect. It incremented an
epoch to prevent stale callback effects; however a long-lived
GObject buffer could still retain callback closures unnecessarily
across repeated lock/unlock or prompt replacements.

The source-only hardening now stores
`_bufferSignalId` and calls `buffer.disconnect(id)` during
`_invalidateSignals()` **before dropping buffer references**.
The epoch increments first, so a disposed or late callback remains
harmless. Teardown is idempotent and catches already-disposed
GObjects. The architecture remains exactly as before: observe only
password-buffer length, never contents or individual key events.

The new automated test simulates a buffer swap, double teardown,
and a disposed buffer to protect against regression.

**Deployment status:** The change is committed in the repo but NOT
installed in the VM or on BlackPearl. Existing tested M8/GDM visuals
and host authentication stay untouched.

## Important intentional behavior differences

- The GNOME lock screen has no account selection; GDM must preserve
  native session/user controls and SHOW LOGIN recovery.
- GDM caches the selected nebula during LoginDialog replacement;
  the lock screen chooses its scene per lock cycle.
- The GDM grid scan recovers from mid-session resize; M8's approved
  implementation differs. The shared scan *geometry/state* remains
  identical. A further visual-parity change would need its own
  VM test before shipping.
- M8 currently calls `cancelIntro()` during an authentication failure,
  whereas GDM deliberately keeps its 5s scan alive. This is an
  **existing behavior difference**, not a newly introduced change.
  Recommend addressing it only with explicit visual testing, not
  silently while hardening signal lifecycle.

## Next operational verification (read-only)

For actual performance numbers, use two separate controlled sessions
with an idle desktop/login, wait through at least three scan cycles,
then sample the GNOME Shell greeter process RSS, CPU time and its
journal diagnostics. GNOME Shell is a shared compositor, so process
CPU cannot be attributed solely to Mellon. Compare an extension-off
VM baseline if quantitative overhead is needed. Do not restart GDM
or disable the working extension on BlackPearl.

**Before production deployment:** test lock observer disconnection
inside the VM, run repeated lock/unlock and login/logout cycles,
stress display resizing and SHOW LOGIN, retain the already verified
offline VM snapshot and a genuinely tested rollback. No host login
changes are authorized.
